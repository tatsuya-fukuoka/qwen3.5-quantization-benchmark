# 量子化の精度劣化実測 — 検証設計 v3（確定）

作成: 2026-11-09（v3: 対象モデルを Qwen3.5-9B に変更。v2 からの変更点は「対象モデル」節と各 Track の注意書き）
確定: 2026-11-09、ユーザーが v3 で確定
位置づけ: 有料記事（note）向けの別検証テーマ。日本語RAG本・第2テーマ（vLLM／llm-d本）とは出し分ける。こちらは「量子化の品質側」の話に絞る。

## ユーザー指示（2026-11-09）

1. 対象モデルはインパクト重視。Qwen2.5 は古いので、Qwen 系で比較的新しく、検証に使えて、一般的に使われているモデルにする
2. GGUF では imatrix 量子化も試す
3. llama.cpp だけでなく vLLM も一般的に使われているので、llm-compressor（https://github.com/vllm-project/llm-compressor）で量子化したモデルも試す

## 目的

日本語 LLM を量子化すると、日本語の性能がどれだけ落ちるかを同一条件で実測する。記事の核は対価表（量子化条件 × スコア低下 × ファイルサイズ × 速度）と、次の3つの問い。

- 何 bit までなら実用か、どこから壊れるか
- imatrix は低 bit で本当に効くのか（同じ bit 幅での標準量子化との差）
- GGUF（llama.cpp 系）と vLLM 向け量子化（FP8／GPTQ／AWQ）で、同じ「4bit 級」でも劣化の出方は違うのか

## 対象モデル

**`Qwen/Qwen3.5-9B`**（2026年3月、Apache-2.0、総パラメータ約9.7B）

- v2 の Qwen3-8B から変更する。理由はインパクト：2026年3月リリースの現行世代で、9B 級ながら言語ベンチの公表値が高い（MMLU-Pro 82.5 等）。「新しいモデルの量子化耐性」という看板が立つ
- 訂正：v2 で「Qwen3.5 世代は llama.cpp の GGUF フローが未対応」と書いたのは誤りだった。llama.cpp は 2026-02-10 の変更（PR #19468）で qwen35 アーキテクチャに対応済みで、unsloth の GGUF も流通している
- 構造上の注意（設計に組み込む）
  - マルチモーダルモデル（Vision Encoder 付き）。今回の評価はテキストのみなので、両 Track とも **言語モデル部分だけ** を対象にする（Track B は vLLM の `--language-model-only`、Track A は mmproj なしの GGUF）。記事にもその前提を明記する
  - ハイブリッド構造（Gated DeltaNet の線形注意 + 通常注意）。フル注意層が 32 層中 8 層だけなので KV キャッシュは小さく、VRAM 見積りでは有利に働く
  - thinking が既定 ON。採点タスクでは OFF に固定する（llama.cpp は `--chat-template-kwargs` で指定）。効いているかは Phase 0 で実出力を見て確認する
- VRAM：BF16 は全体で約19GB。L4（24GB）ではテキストのみ・評価用にコンテキストを絞れば載る見込みだが余裕は薄い。Track B の BF16 基準が L4 で詰まる場合は A100（40GB級）へ切り替える判断を Phase 0 で行う
- 除外した候補と理由: Qwen3-14B は FP16 が約28GB で L4 に載らず不採用（v2 時点の判断を維持）。Qwen3-8B は v3 の予備候補として残す（Qwen3.5-9B がツール側の理由で詰まった場合の切替先）

## 比較条件

### Track A: llama.cpp／GGUF（自前で量子化し、条件を完全統制する）

HF の BF16 から GGUF へ変換し、`llama-quantize` で自分で量子化する。配布済み GGUF は使わない（bartowski 版などは全量子化が imatrix 前提で作られており、「imatrix の有無」だけを変数にできないため）。
注意：qwen35 対応は新しいため、llama.cpp は最新ビルドをソースからビルドして使う（Colab では元々ソースビルドする前提）。変換（`convert_hf_to_gguf.py`）は言語モデル部分のみを対象にする。

| ID | 条件 | 備考 |
|---|---|---|
| A0 | F16 | Track A の基準 |
| A1 | Q8_0（標準） | |
| A2 | Q5_K_M（標準） | |
| A3 | Q4_K_M（標準） | |
| A3i | Q4_K_M（imatrix） | A3 と同 bit 幅で imatrix の効果だけを見る |
| A4 | Q3_K_M（標準） | |
| A4i | Q3_K_M（imatrix） | imatrix が効くとされる低 bit 域 |
| A5 | Q2_K（標準） | |
| A5i | Q2_K（imatrix） | 壊れ始めと imatrix の救済効果を見る |

- imatrix は `llama-imatrix` で生成する。キャリブレーションには、日本語コミュニティで実績のある公開データセット `TFMC/imatrix-dataset-for-japanese-llm` の `c4_en_ja_imatrix.txt`（日英混合）を使う（ユーザーの note 記事の手順を参考にした。再現性のため公開データセットを正とする）。`--chunks` は記事の実績値 32 を起点にする
- 任意の拡張（時間が余れば）: 日本語のみ（Wikipedia 日本語版の抜粋）で作った imatrix を Q4_K_M に1条件追加し、「キャリブレーションの言語構成は効くのか」を見る
- 参考行（任意）: IQ4_XS（imatrix 必須の IQ 系）。K 系との直接比較ではなく、IQ 系の実力を見る位置づけ

### Track B: vLLM + llm-compressor（自前で量子化する）

llm-compressor の `oneshot` で自分で量子化し、compressed-tensors 形式で vLLM に載せる。Track 内は同一ランタイムなので生成速度も比較できる。
注意：(1) Qwen3.5 の vLLM 対応はモデルカード上「main ブランチ（nightly）が必要」とされており、Colab では nightly の vLLM を入れる。(2) 量子化は言語モデルの Linear 層だけを対象にし、Vision Encoder は BF16 のままにする（RedHatAI の Qwen3.5 系量子化も同方針）。(3) ハイブリッド構造に対する GPTQ／AWQ の実績は Qwen3 系より薄いので、Phase 0 で FP8（B1）を通して早期に可否を判定する。

| ID | 条件 | 備考 |
|---|---|---|
| B0 | BF16（vLLM） | Track B の基準 |
| B1 | FP8 dynamic | キャリブレーション不要の W8A8 |
| B2 | GPTQ W4A16 | キャリブレーションは日本語 512 サンプル |
| B3 | AWQ W4A16 | キャリブレーションは B2 と同一 |

## 評価（全て日本語、プロンプト固定、greedy decoding、thinking OFF）

1. JCommonsenseQA — accuracy（常識推論）
2. JSQuAD — F1／EM（読解）
3. MGSM — exact match（計算推論。量子化で壊れやすい代表）
4. 日本語 perplexity — 固定コーパス抜粋で測る劣化の連続量
5. 定性評価 — 固定10プロンプトの生成例を全条件で保存する（記事に載せる）

- 件数: スモークでは各100件、本測定では各200件（MGSM は全250件）を基本とし、所要時間を見て確定する
- 副次指標: ファイルサイズ、VRAM 使用量、生成速度（tok/s。Track 内でのみ比較）

## 実行環境とフェーズ分け

条件が13あるので、Colab の無料セッションに収まるよう3フェーズに分ける。

- Phase 0（スモーク）: A0／A3／A3i／B1 の4条件だけを各100件で回し、ハーネスの形式・採点・所要時間を確認する
- Phase 1: Track A の残り（A1／A2／A4／A4i／A5／A5i）
- Phase 2: Track B の残り（B0／B2／B3。B1 は Phase 0 で実施済み）

- ランタイムは **L4（24GB）** を基本とする: Qwen3.5-9B の BF16 は約19GBと余裕は薄いが、テキストのみ＋評価用にコンテキスト長を絞る（例：8192）前提で載せる。ハイブリッド構造のため KV キャッシュは小さい。Phase 0 で VRAM 不足が出たら、その時点で A100（40GB級）へ切り替える
- 実装（量子化スクリプトと評価ハーネス）はこの環境の Claude Code に指示し、Muse がレビューする。Colab での実行操作はブラウザ経由で Muse が行い、Google サインインはユーザーが公式画面で実施する
