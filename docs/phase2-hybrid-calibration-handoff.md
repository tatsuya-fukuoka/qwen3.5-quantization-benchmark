# Phase 2 依頼: ハイブリッド・キャリブレーション（256 × 1024）の設計と実装

## 決定事項（ユーザー決定 2026-11-09）

- B2（GPTQ）／B3（AWQ）のキャリブレーションは **ハイブリッド案** で組み直す:
  - 既存コーパス `data_main/imatrix_calib.txt`（TFMC `c4_en_ja_imatrix.txt`、120文書）のトークン列を**全量**使う（実測: 文書ごとトークナイズの合計 93,306 トークン）。
  - 不足分を**公開日本語テキストで補充**し、全体を 1 本のトークン列に連結（パッキング）して **1024 トークン × 256 サンプル = 262,144 トークン** を切り出す（GPTQ 論文の総トークン量と同量）。
  - B2／B3 では完全に同一のサンプル集合を使う。
- 土台となる調査: `docs/calibration-512-investigation.md`、`docs/calibration-256-investigation.md`、`docs/llmcompressor-0150-calibration-source-check.md`（0.15.0 では、トークナイズ済み Dataset はそのまま返り連結処理は効かない／既定ではパディングは発生しない、まで確認済み）。

## 設計で決めること（設計書に明記する）

1. **補充ソース**: 第一候補は `HuggingFaceFW/fineweb-2` の `jpn_Jpan`（train、ODC-By 1.0）を Hugging Face のストリーミングで取得する。代替候補（`wikimedia/wikipedia` の `20231101.ja`、CC BY-SA）との比較と、どちらを採用するかの理由を書く。Colab での取得方法（streaming の可否、ダウンロード量の見積もり）も設計に含める。
2. **必要トークン量の計算**: 262,144 − 93,306 = 168,838 トークンが最低限の補充量。プールに余裕を持たせる方針（例: プールのチャンク数が 256 を少し上回るまで文書を取り、seed 固定で 256 件を抽出する）かどうかを決め、理由を書く。
3. **連結順と決定性**: 既存コーパスと補充分の連結順、文書のシャッフル（seed とバッファサイズ）、トークナイズ条件（`add_special_tokens=False`、文書境界の扱い）を固定する。再現性のために記録すべき項目（データセット名・config・revision が取れるか、消費した文書数と文書 ID、seed）を列挙する。
4. **再現性の担保**: 生成したパック済みキャリブレーション（256 × 1024 のトークン ID 列）は小さい（数 MB 級のはず）ので、ノートブックの準備段階で GitHub にも保存し、ランタイム再開時はそれを優先して使う設計を検討する（`.gitignore` の扱いも含めて設計書に書く）。採否と理由を明記する。
5. **検証設計 v3 との整合**: Track B のキャリブレーション記述は「512 サンプル」から「256 サンプル × 1024 トークン、既存コーパス＋日本語公開テキストのハイブリッド」に変わる。設計書に、設計書 v3 へ当てる修正文案と、記事での説明文案（2〜3 文）を入れる。v3 本文そのものの修正は今回の範囲外（メイン側で行う）。
6. **Track A との関係の正直な記述**: Track A の imatrix と Track B のキャリブレーションは出典が完全には同一でなくなる。その留保を記事でどう書くかの文案も入れる。

## 実装すること

土台: 現在の `scripts/quantize_w4a16.py`、`colab/phase2_main_b.ipynb`、`scripts/prep_data.py`。

1. **キャリブレーション構築の分離**: パック済みキャリブレーションを作る処理を独立させる（例: `scripts/build_calibration.py`）。入力は既存コーパスのテキストファイルと補充ソース、出力はパック済みトークン ID 列のファイル（形式は設計で決める。JSON 等の単純な形式）＋構築メタ情報（JSON）。Colab のノートブックから呼ぶ。
   - パッキングの純関数部分（トークン ID 列のリスト → 連結 → 固定長チャンク → 端数破棄 → seed 抽出）は torch 不要でテスト可能に分離する。
2. **`quantize_w4a16.py` の改修**: `--calib-packed` のように、パック済みファイルを直接読んで Dataset（`input_ids`／`attention_mask`）を作る経路を追加する。既存の行ベース経路（`--calib-text`）は後方互換として残すが、B2／B3 のノートブックは新経路を使う。
   - `quant_meta.json` の `calibration` に、方式（hybrid-pack）、サンプル数 256、系列長 1024、総トークン数、出典内訳（既存／補充のトークン数）、seed、パック済みファイルの sha256、`samples_sha256`（ID 列ベース）を記録する。
3. **ノートブック `phase2_main_b.ipynb` の改修**:
   - 準備セルで補充ソースを取得し `build_calibration.py` でパック済みキャリブレーションを生成する（既にあればスキップ。再現性担保の設計に従う）。
   - B2／B3 の呼び出しを新経路に切り替える。B0／B1 のセル・結果・push の仕組み（条件ごと push、`summary_b.tsv`／`timings_b.tsv` の分離、「PUSH FAILED」警告）は壊さない。
   - セル構成を変えた場合は、ノートブック内の説明文も実態に合わせる。
4. **テスト**: 既存テスト全件（35 件）が通ることに加え、新規の純関数テストを追加する: (a) 同じ入力・seed で再現する (b) 全サンプルが 1024 トークンちょうど (c) 端数が捨てられる (d) プール不足で例外 (e) 重複チャンクが無い（抽出時） (f) ダミートークナイザでの構築経路。ダミーの補充テキストで `build_calibration.py` の疎通も確認する（実データのダウンロードはこの VM では無理にしない。できない場合はその旨を報告する）。
5. **設計書**: `docs/calibration-hybrid-design.md` に、上記の設計判断・計算・文案・変更一覧をまとめる。

## 制約・禁止事項

- 評価データ（JCSQA／JSQuAD／MGSM／PPL 用テキスト）はキャリブレーションに使わない。
- 重複サンプリングやオーバーラップで水増ししない。
- B0／B1 の完了済み結果（`results_main/B0.json`、`B1.json`）と Track A の成果物には触れない。
- GPU 不要、課金なし。Colab の実行はしない（実装とテストまで）。
- 不明点は推測で埋めず「未確認」と書く。
