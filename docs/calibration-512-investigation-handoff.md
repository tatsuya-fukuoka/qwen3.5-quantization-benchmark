# Phase 2 調査依頼: GPTQ／AWQ のキャリブレーション 512 サンプルを維持する方法

## 背景（確定事実）

- Phase 2（Track B）の B2（GPTQ）量子化が開始直後に失敗した。エラー原文: `キャリブレーション候補が不足: 120 行 < 512（min_chars=64）`。量子化処理自体は始まっていない。B0（BF16）・B1（FP8）は完了し GitHub 保存済み。B3（AWQ）未開始。
- 原因は `scripts/quantize_w4a16.py` の `build_calibration_samples` が `data_main/imatrix_calib.txt`（= HF データセット `TFMC/imatrix-dataset-for-japanese-llm` の `c4_en_ja_imatrix.txt`）から「64文字以上の行」を 512 件要求するが、候補が 120 件しかないこと。
- ユーザーの決定（2026-11-09）: **サンプル数を 120 に落とさず、512 を維持する方向で方法を調査する**。今回は調査のみで、`quantize_w4a16.py` の挙動は変更しない。

## Muse 側で実測済みの基礎数値（再現確認すること）

ファイルを実際に取得して数えた値（`curl -sL https://huggingface.co/datasets/TFMC/imatrix-dataset-for-japanese-llm/resolve/main/c4_en_ja_imatrix.txt`）:

- ファイルサイズ 406,475 バイト。改行で割ると 239 片、うち空行 119（文書は空行区切り）。
- 実文書は **120 件**で、全て 64 文字以上（最小 68 文字）。文字数合計 290,239、中央値 1,687 文字、最大 16,318 文字。つまり「行数」は少ないが 1 文書は長い。
- 日本語文字（ひらがな・カタカナ・漢字）の比率は約 17.7%（残りは英語中心の C4 由来テキスト）。
- 粗い正規表現での文分割の概算: 文総数 約 2,915、64 文字以上の文 約 1,623。
- 文字チャンク分割の概算（文書ごと・重なりなし）: 512 文字チャンクで 628 件、700 文字で 472 件、400 文字で 786 件。

## 調査タスク

### 1. 基礎統計の再現と拡張

- ファイルを自分で取得し、上記の数値を再現する。
- `Qwen/Qwen3.5-9B` のトークナイザで全文の総トークン数を実測する（トークナイザ単体の取得で足りる。モデル本体 19GB は落とさない）。
- 連結チャンク方式（全文をトークナイズして固定長に切る）で、系列長 512／256／128 のそれぞれで何サンプル得られるかを実測する。

### 2. 候補方式の評価

以下の各方式について、「512 サンプル得られるか（実測）」「サンプルの長さ分布（文字数・トークン数の平均とばらつき）」「実装変更の範囲」「B2／B3 で完全に同一サンプルにできるか」を評価する。

- A. 文分割: 文書を文単位に割り、512 文を seed 固定で抽出する。短い文が混ざる影響（GPTQ／AWQ のキャリブレーションとして短すぎないか）も考察する。
- B. 文字チャンク分割: 各文書を固定長チャンクに割る。文の途中で切れることの影響を考察する。
- C. トークンチャンク: 全文をトークナイズし固定トークン長で割る。`max_seq_len`（現在 512）との整合と、oneshot 側の扱い（既にトークナイズ済みデータセットを渡せるか）を確認する。
- D. 別コーパスで補充: 同じ HF データセット内の他ファイルの構成を確認し、使えるものがあるか。また別の公開日本語コーパスで補う場合の候補（入手方法・ライセンス・日英比率への影響）。ただし Track A の imatrix と同じ出典であることの意味（比較の語りへの影響）も考察する。
- E. その他、妥当な方式があれば追加する。

### 3. 禁止事項

- 評価データ（JCommonsenseQA／JSQuAD／MGSM、および PPL 用テキスト。いずれも `data_main/` の評価側ファイル）はキャリブレーションに**使わない**。混入は検証の独立性を壊すため、候補に挙げる場合も却下理由として明記する。
- 512 件に届かせるための重複サンプリング（同じ文の複製で水増し）は、原則として候補にしない。挙げる場合はその問題点を明記する。

### 4. 実務上の目安の整理

- GPTQ／AWQ のキャリブレーションで一般に使われるサンプル数と系列長の目安を、llm-compressor の公式ドキュメント／サンプルコード等の根拠とともに整理する。「512 件」という数字自体が必須なのか、総トークン量のほうが本質なのかも含める。根拠が確認できない点は「未確認」と明記する（推測で断定しない）。

### 5. 推奨案

- 推奨を 1 つに絞り、理由を述べる。
- 検証設計 v3 の記述（Track B は「日本語キャリブレーション 512 サンプル」）との整合と、記事に書く場合の説明文案（1〜2 文）を提示する。
- 次に実装する場合の変更見取り図（対象関数・引数・`quant_meta.json` への記録項目・追加テスト案）を示す。実装そのものはしない。
