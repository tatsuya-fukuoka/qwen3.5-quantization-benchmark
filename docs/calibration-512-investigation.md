# Phase 2 調査: GPTQ／AWQ のキャリブレーション 512 サンプルを維持する方法

調査日: 2026-11-09 / 依頼: `docs/calibration-512-investigation-handoff.md` / 調査のみ（`scripts/quantize_w4a16.py` は未変更）

## 結論（先に）

- コーパス全体が **93,425 トークン**（Qwen3.5-9B トークナイザ）しかない。「512 サンプル × 系列長 512」（= 262,144 トークン）は、**どの方式でも原理的に不可能**。512 サンプルを維持するなら系列長を短くするしかない。
- 重複なしで 512 サンプル得られる方式は A（文）・B（文字チャンク）・C（トークンチャンク、系列長 ≤182）。
- **推奨: C'（文書ごとのトークンチャンク、長さ 128、seed 固定で 512 件を抽出）**。512 件を保ち、総トークン量は 65,536 と現行方式（120 文書を 512 で切り詰めて 40,984）より多く、全サンプルが同一長で、B2／B3 で完全に同一にできる。
- 「512 件」自体が必須かどうかは、公式資料の範囲では**裏付けなし**（下記 §4）。ただしユーザー決定（512 維持）に従い、上の推奨にした。

### 連結チャンク方式（トークン固定長、端数は捨てる）

| 系列長 | 全文連結（C） | 文書ごと（C'） | 512 サンプル必要トークン数 | 512 件得られるか |
|---|---|---|---|---|
| 1024 | 91 | 49 | 524,288 | ✗ |
| **512** | **182** | **130** | 262,144 | **✗** |
| 256 | 364 | 308 | 131,072 | ✗ |

| 64 | 1,459 | 1,396 | 32,768 | ✓ |

全文連結で 512 件になる最大の系列長は 182（= 93,425 ÷ 512）。**系列長 512／256 では 512 件に届かない**。

## 2. 方式比較

「512 件が得られるか」はすべて実測。各方式とも seed=0 で重複なしに 512 件を抽出（プールは重複除去・ソート後に `random.Random(0).sample`）。

| 方式 | 512 件 | プール | 文字数（平均±標準偏差／中央値） | トークン数（平均±標準偏差／中央値／p10〜最大） | 総トークン量 | B2／B3 同一 | 実装変更範囲 |
|---|---|---|---|---|---|---|---|
| 現行（行＝文書） | ✗（120） | 120 | 2,419±2,916／1,687 | 777±1,288／403 | 40,984（512 切詰め） | ○ | — |
| A. 文分割 | ✓ | 1,611 | 139±117／115 | 41.6±72.8／30（17〜1,089） | 21,317 | ○ | 小 |
| B. 文字 512 チャンク | ✓ | 609 | 478±94／512 | 155±99／111（13〜434） | 79,582 | ○ | 小 |
| C. トークン連結（長さ 128） | ✓ | 729 | — | 128 固定 | 65,536 | ○（※） | 中 |
| **C'. 文書ごとトークン（長さ 128）** | ✓ | 669 | — | 128 固定 | 65,536 | ○（※） | 中 |
| C/C'（長さ 512 または 256） | ✗ | 182／130、364／308 | — | — | — | — | — |
| D. 別コーパス補充 | 未実測（§2-D） | — | — | — | — | — | 大 |

※ トークンチャンクはトークナイザのバージョンが変わると切れ目が変わりうる。保存した ID 列のハッシュ（`samples_sha256`）を B2／B3 で突き合わせれば同一性を担保できる。

### A. 文分割
- 512 件は得られる（プール 1,611 文から 32% を抽出）。
- 欠点: トークン中央値 30、p10 は 17 と**非常に短い**。総トークン量は 21,317 で、コーパス全体の 23% しか使わない。1 サンプルが 1 文なので、長い文脈での活性化の分布を反映しにくい。文分割は粗い正規表現なので、略語（"Mr." 等）の誤分割もありうる。
- GPTQ／AWQ のキャリブレーションとして短すぎるかどうかを示す公式の根拠は**未確認**。ただしトークン量が現行の約半分になる点は確実。

### B. 文字チャンク分割
- 512 件得られる（プール 609、抽出は 84%）。総トークン量 79,582 は最大。
- 文字数ベースなので文や単語の途中で切れる。トークン長は 13〜434 とばらつく（英語部分と日本語部分で文字／トークン比が違うため）。日本語は 1 文字≒1 トークン前後、英語は約 4 文字／トークンなので、日本語チャンクのほうがトークンが多い。
- プールの 84% を使うため、512 件は元コーパスのほぼ全域を覆う。

### C. トークンチャンク（全文連結）／C'. 文書ごと
- 全文トークナイズして固定長に切る。**系列長 128 なら 729 件（C）／669 件（C'）で 512 件を確保**できる。
- 系列長が揃うので、バッチ時のパディングが無い。C は文書の境界をまたぐ（無関係な文書が 1 サンプルに混ざる）。C' は文書内で切るので混ざらない。端数は捨てる。
- `max_seq_len`（現在 512）との整合: 128 のサンプルは 512 に達しないので切り詰めは起きない。`--max-seq-len 512` のままでも動くが、実態と食い違うので、`quant_meta.json` には実際のサンプル長（128）を別項目で記録すべき。
- oneshot 側: **トークナイズ済みの `datasets.Dataset` を `dataset=` に直接渡せる**ことを llm-compressor 公式の `examples/custom_dataset_example.py`（main）で確認した。現行スクリプトも同じ形（`input_ids`／`attention_mask` の Dataset）で渡している。チャンク ID から同じ形の Dataset を作れば受け付けられるはずだが、**0.15.0 での実機確認はしていない**（未確認）。
- oneshot の引数 `concatenate_data`（連結して `max_seq_length` を埋める）が main の `dataset_arguments.py` に存在する。ただし 0.15.0 での挙動と、トークナイズ済み Dataset に対しても効くかは**未確認**。自前でチャンクするほうが再現性の面で安全。

### D. 別コーパス
- 同じ HF データセット内に他ファイルは無い（上記）ので、同一出典内の補充は不可能。
- 他コーパスの候補（ライセンスは HF API のタグで確認。日英比率への影響は未実測）:
  - `wikimedia/wikipedia`（ja）: cc-by-sa-3.0 と gfdl。日本語 100%。
  - `allenai/c4`（ja 部分）: odc-by。imatrix データの出典（C4）と同系統。
  - `HuggingFaceFW/fineweb-2`（jpn）/ `hotchpotch/fineweb-2-edu-japanese`: odc-by。
  - `range3/cc100-ja`: ライセンスタグ unknown（使用不可と扱うのが安全）。
- 影響: Track A の imatrix と同じ出典（TFMC の c4_en_ja_imatrix）を使う現設計は「Track A と B で較正データが同源」という語りが成り立つ。別コーパスで補うと、日英比率（現状は日本語文字 約 17.7%）が変わり、**Track A（imatrix）との比較の語りが弱まる**。また、補充分は 2 つの出典が混ざった較正セットになり、検証設計 v3 の「日本語キャリブレーション」との整合も説明が必要になる。
- 結論: 512 件を満たすだけなら D は不要（C' で足りる）。D は実装・ライセンス確認・説明のコストが最大なので推奨しない。

### E. その他
- **重複サンプリング（同じ文／チャンクの複製で水増し）**: 却下。同じデータが複数回入るだけで情報量は増えず、「512 サンプル」の見かけだけが水増しになる。ヘッシアン（GPTQ）や活性化統計（AWQ）が重複した部分に偏る。依頼の禁止事項にも該当。
- **オーバーラップ付きチャンク（スライディング窓）**: 512 件を得る手段としては可能だが、実質重複が混ざる（重複の弱い形）。長さ 128・ストライド 64 なら約 1,400 件だが、各トークンが 2 回入る。依頼の趣旨に反するので採用しない。
- **評価データの使用**: JCommonsenseQA／JSQuAD／MGSM、PPL 用テキストは較正に**使わない**。コーパスが足りない状況では魅力的な「補充元」に見えるが、較正データと評価データが重なると量子化後の精度が過大評価され、検証の独立性が壊れるため却下。なお、今回の VM には `data_main/` が無く、本コーパスと評価データの重複有無は**未確認**（今回は評価データに触れていない）。

## 3. 現行コードとの関係（事実のみ）

- `build_calibration_samples` は「行＝文書」を前提にしている（docstring は「1 行 1 文書」）。実ファイルでは 1 文書が 1 行だが、文書間に空行が入るため、行数は 239、空行を除いた 120 件が候補。これが B2 失敗の直接原因。
- 現行は 512 を超える文書を `MAX_SEQ_LEN=512` で切り詰める。120 文書のうち実効トークンは 40,984。
- oneshot の `shuffle_calibration_samples` の既定は True（main）。`num_calibration_samples=len(samples)` なので全件使われ、順序が変わるだけ。順序が B2／B3 で異なっても使うサンプルの集合は同じ。

## 4. 実務上の目安（根拠つき）

確認元: `vllm-project/llm-compressor` の main（コミット 18243db、2026-11-06）。**本プロジェクトで使っているのは llmcompressor 0.15.0**（`results/B1.json`）なので、main と 0.15.0 の差は**未確認**。例として、main の AWQ サンプルは `llmcompressor.modifiers.transform.awq` から import しているが、本プロジェクトは `llmcompressor.modifiers.awq` を使っており、API が変わっている。

| 根拠 | サンプル数 | 系列長 |
|---|---|---|
| `examples/quantization_w4a16/README.md`（GPTQ W4A16） | 「512 samples is a good place to start (increase if accuracy drops)」 | 「2048 sequence length is a good place to start」 |
| `examples/quantization_w4a16/llama3_example.py` | `num_calibration_samples=512` | `max_seq_length=2048` |
| `examples/awq/llama_example.py` | `num_calibration_samples=256` | `max_seq_length=512` |
| `src/llmcompressor/args/dataset_arguments.py` | `num_calibration_samples` の既定 512 | `max_seq_length` の既定は None |

- 公式は「512 件」を**出発点（good place to start）**として示しており、必須条件とは書いていない。AWQ の公式サンプルは 256 件×512 トークンで、512 件が必須ではない傍証になる。
- 「総トークン量のほうが本質か」について、公式資料からは**断定できない**（未確認）。GPTQ はヘッシアン推定、AWQ は活性化統計に較正トークンを使うので、直感的にはトークン総量が効くはずだが、公式の記述や本プロジェクトでの実測は無い。
- 較正セットのスケール感: 公式例の 512×2048 ≈ 1,048,576 トークン、AWQ 例の 256×512 = 131,072 トークンに対し、本コーパスは全体で 93,425 トークン。**公式の AWQ 例の 71% が上限**で、C' の 65,536 は AWQ 例の約半分。つまりコーパスの制約上、公式例の水準には届かない（どの方式でも）。
- 公式は「実運用データに近い較正データが望ましい」とも書いている（w4a16 README）。評価が短い質問文中心なら短い系列も合理的だが、評価プロンプトの長さ分布は今回**未調査**。

## 5. 推奨案

### 推奨: C'（文書ごとのトークンチャンク、長さ 128、seed=0 で 512 件抽出）

理由:
1. **512 件を重複なしで確保**できる（プール 669 件から抽出）。ユーザー決定に合致。
2. 総トークン量 65,536 は現行の 120 サンプル案（実効 40,984）より多く、A（21,317）より大幅に多い。B（79,582）には劣るが、全サンプルが同長で扱いやすい。
3. 同一出典（Track A と同じ imatrix データ）のまま、日英比率も変えない。
4. 同じ入力・seed・トークナイザなら完全に決定的で、ID 列のハッシュで B2／B3 の同一性を検証できる。
5. 文書をまたいで混ぜない（C との違い）。

弱点（隠さず記載）: 系列長 128 は公式の目安（512〜2048）よりかなり短い。Qwen3.5 は線形注意系の層を含むと見られるが（B0 の Mamba cache の件から）、短い系列で量子化精度にどう影響するかは**未確認**。B（文字 512 チャンク、トークン 13〜434）は自然な長さのばらつきを持つ代替案で、総トークン量が最大。精度を重視して長さを稼ぎたいなら B を次点とする。

### 検証設計 v3 との整合と説明文案

v3 の「日本語キャリブレーション 512 サンプル」は件数については満たせる。ただし「各 512 トークン」ではなく「各 128 トークン」である点は v3 の文言に含まれていないので、記事や設計書には長さを明記すること（v3 本文の修正は今回の範囲外）。

記事の説明文案（1〜2 文）:
> キャリブレーションには Track A の imatrix と同じ日英混在コーパス（C4 由来、約 9.3 万トークン）を使い、文書内で 128 トークンごとに区切った 669 区間から seed 固定で 512 サンプルを抽出した（GPTQ と AWQ で完全に同一）。コーパスの総量が 512×512 トークンに満たないため、サンプル数を 512 に保つ代わりに系列長を 128 に短縮している。

### 次に実装する場合の変更見取り図（実装はしない）

- 対象関数: `build_calibration_samples`（または新関数 `build_calibration_token_chunks`）。
  - 文書分割: 空行区切り（現行の「行＝文書」から変更）。
  - トークナイズは quantize_w4a16.py 側（`main()`）に寄せ、関数は「文書のトークン ID 列のリスト」を受けて、長さ L で切って端数を捨て、`random.Random(seed).sample` で n 件返す純関数にする（torch 無しでテスト可能に）。
- 引数: `--chunk-tokens`（既定 128）、`--chunk-mode {doc,line}`（`line` は現行互換）。`--max-seq-len` は チャンク長以上であることを検証。
- Dataset: `{"input_ids": [...], "attention_mask": [1]*L}` を直接作って `oneshot(dataset=ds, max_seq_length=L, num_calibration_samples=512)`。再トークナイズはしない。
- `quant_meta.json` への記録項目: `chunk_tokens`、`chunk_mode`、`tokenizer_name`、`tokenizer_version`（transformers／tokenizers）、`pool_size`（669）、`num_samples`、`seed`、`total_calib_tokens`、`corpus_sha256`（入力ファイル）、`samples_sha256`（ID 列ベースに変更）、`split` の説明文。
- 追加テスト案: (a) 同じ入力・seed で 2 回作って一致、(b) 全サンプルの長さが L、(c) 文書境界をまたがない、(d) プール < n で例外、(e) 重複サンプルが無い、(f) 既存の `--chunk-mode line` が現行の結果と一致（後方互換）、(g) ダミー・トークナイザ（文字コードを ID にする）でトークンありの経路を torch 無しで確認。
- B2 の失敗を再現する回帰テスト: 120 文書だけの入力が、line モードでは例外になり doc モードでは 512 件得られること。
